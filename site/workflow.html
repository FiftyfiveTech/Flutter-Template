02 / Documentation

The 8-step AI development loop.

💡

Build the documentation before the code. Define your design tokens, features, screens, architecture, and development rules first. Then let your AI assistant implement against those decisions, one flow at a time. Tap a step to expand it.

01
Design Tokens + PRD Generate colors, typography, and spacing from your PRD into docs/design_systems/tokens/, before any screens exist.
⌄

Paste your PRD into an AI design tool and generate design tokens (colors, typography, spacing, radii) as CSS variables or JSON before any screens exist. Save them under docs/design_systems/tokens/, mirrored into Flutter's ThemeExtension — never hardcode a value in feature code.

Improvement: also ask for the rules of usage alongside the tokens (when to use semantic vs. brand color, contrast minimums, spacing increments) in the same pass — backfilling this later costs more than asking for it up front.
Prompt 1 — Design Tokens + PRD 
We are building a production-grade Flutter application. Here is our PRD:
[Paste PRD here]

Based on this PRD, create a tokenized design system. Include:
1. Color palette (primary, secondary, semantic accents, neutrals, surfaces).
2. Typographic scale (sizes, line heights, weights).
3. Spacing grid, radius scale, shadow scale, and motion/easing tokens.
4. A short usage-rules note per category.
Output as CSS custom properties (or a token JSON) plus a one-page rationale.
Do not write Dart code yet.
02
Feature Breakdown Parse the PRD into a numbered list of features. One spec file per feature under docs/features/, plus an index.md.
⌄

Ask the AI to parse the PRD into a numbered list of independent feature areas. Create one spec file per feature under docs/features/ plus an index.md, capturing user stories, data entities, and dependencies on other features.

Improvement: do this before any screen mockups, not interleaved with them. Doing it first gives the design tool a stable feature vocabulary to tag every screen with — which pays off in Step 7 when you ask for "the X flow."
Prompt 2 — Feature Spec Breakdown 
Here is our PRD: [reference or paste it].

Break it into a numbered list of feature areas. For each feature, produce a
spec file containing:
1. User stories / jobs-to-be-done.
2. Data entities and screens touched.
3. Dependencies on other features (call out cross-feature imports).
4. Safety, security, or regulatory constraints specific to this feature.
Also produce an index.md listing every feature file.
03
Screen Generation Outline every screen state — loaded, loading, empty, error, offline — and index each one in docs/screen_flow.md.
⌄

Develop detailed screen outlines feature-by-feature. Identify empty states, loading indicators, offline layouts, and validation error designs. Keep a running screen index under docs/screen_flow.md.

Improvement: from day one, also produce a master screen index (screen ID → composing widgets → which feature/flow it belongs to) plus a dedicated cross-cutting states file (offline banner, skeleton loaders, empty states, generic error) shared across all screens — building these now saves a rework pass once you notice states being reinvented per-screen.
Prompt 3 — Feature-by-Feature Screens 
Using our design tokens and the feature spec for [Feature Name], generate
the screen layout guidelines. Include:
1. Every state per screen: loaded, loading/skeleton, empty, error, offline.
2. A screen ID for each screen (e.g., ONB-01, SET-02).
Add each new screen ID to docs/screen_flow.md. Do not write Flutter widgets yet.
04
Architecture Docs Detail database schemas, network paths, and the source of truth for every computed value in docs/architecture.md.
⌄

Detail the database schemas, network paths, and local caching decisions. Document which system acts as the source of truth for each computed value in docs/architecture.md.

Improvement: write down known conflicts between the design mockups and the PRD as you find them, in a living doc, rather than resolving them silently in code — a future session needs to know a decision was made and why, not just see the resulting code.
Prompt 4 — Technical Architecture 
Based on the PRD and the feature specs, write the technical architecture docs
for this Flutter app:
1. architecture.md — tech stack, folder structure (Clean Architecture per
   feature), state management, local database schema, networking strategy,
   error handling, testing strategy, Definition of Done.
2. A data-flow doc — local schema, remote schema, sync direction, and source
   of truth rules.
3. Explicitly note anywhere this doc supersedes or conflicts with the PRD.
05
CLAUDE.md Rules Encode feature boundaries, state-management rules, and caching/theme expectations as non-negotiable rules.
⌄

Update CLAUDE.md with strict boundaries: feature isolation, the chosen state-management rules, local-first cache expectations, and test coverage targets.

Improvement: link out to the docs from Step 4 rather than duplicating them — CLAUDE.md should be the index of rules, not a copy of the architecture doc. Treat it as living: every skill added in Step 6, or drift Step 8 surfaces, gets written back in here.
Prompt 5 — Rules Index (CLAUDE.md) 
Based on architecture.md and the data-flow doc, generate CLAUDE.md for this
repository:
1. Feature-boundary rules (what a feature may/may not import).
2. State management constraints (Riverpod code-gen rules, no inline widget
   logic).
3. Data caching rules (local-first vs remote-first).
4. Theme rules (no hardcoded color/spacing/typography).
5. Lint/test gates.
Link out to the docs rather than duplicating their content.
06
Equip AI Skills Package durable checklists (architecture audits, design-token checks, overflow tests) as skills under .claude/skills/.
⌄

Equip the AI coding assistant with durable skills at .claude/skills/ (e.g. Clean Architecture scaffolding checklists, design-token check validations, widget overflow tests).

Improvement: add feature-scaffolding, data-sync, and state-management skills at the same time as your first audit/testing skills, rather than one at a time once you notice you're re-explaining the same constraints every session.
Prompt 6 — Equip Skills 
Create a Claude Code skill at .claude/skills/[skill-name]/SKILL.md for:
[Choose: clean architecture auditing | design-token compliance | responsive
layout audits | test generation | feature scaffolding | data-sync wiring].
The skill should act as a checklist for the AI to verify before finishing
feature work, with concrete trigger phrases for when it should auto-fire.
Then add one line to CLAUDE.md's skills section pointing to it.
07
Flow-by-Flow Build Build one logical flow at a time: Domain Entity → Repository Interface → Use Case → Riverpod Controller → Presentation UI.
⌄

Build one logical flow at a time (e.g., onboarding, settings) rather than screen-by-screen. Generate code in order: Domain Entity → Repository Interface → Use Case → Riverpod Controller → Presentation UI.

Improvement: run the responsiveness and audit skills from Step 6 at the end of each flow, not in a separate later pass — catching a boundary violation or overflow bug right after generating a flow is far cheaper than finding it three features later.
Prompt 7 — Flow-by-Flow Implementation 
We are ready to implement the [Feature Name] flow (screens: [screen IDs],
flow doc: docs/screen_flow.md).
Generate the code in this exact order:
1. Domain entity + Repository interface contract.
2. Domain use case (encodes business rules).
3. Riverpod controller/notifier.
4. Presentation widgets using ThemeExtension design tokens.
When finished, run the responsiveness and boundary audit skills against
this flow before moving to the next one.
08
Knowledge Graph Audit Run context-auditing tools like graphify to catch circular imports and boundary violations, feeding fixes back into CLAUDE.md.
⌄

Run context auditing tools (like graphify) to detect circular imports, feature-boundary violations, or missing abstractions, and feed corrections back into CLAUDE.md.

Improvement: don't run this once at the end — re-run it after every few flows in Step 7 and feed drift back into Step 5, so the graph stays a live health check. Pair it with a lightweight memory practice: the graph answers "how is the code connected"; memory answers "what did we decide and why, across sessions" — a long project needs both.
Prompt 8 — Knowledge Graph Audit 
/graphify
Build/refresh the knowledge graph for this workspace. Then report:
1. Any import that crosses a feature boundary CLAUDE.md prohibits.
2. Circular dependencies or orphaned modules.
3. Community hubs large enough to suggest a missing abstraction.
Feed anything found back as a fix task, and flag any rule it exposes that
CLAUDE.md doesn't document yet.
↺

The loop is cyclical, not linear. Findings from Step 8's audit feed back into Step 5 — every circular-import or boundary violation becomes a new rule in CLAUDE.md, not just a one-off fix.

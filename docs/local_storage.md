# Local Database (Drift) Guide

This template uses [Drift](https://drift.simonbinder.eu/) (a typed SQL layer over SQLite) as the
local database engine. This doc explains where it's initialized, which files are responsible for
what, and what's involved if a project wants to replace it with a different local storage plugin.

## Where it's initialized

- `lib/core/database/app_database.dart` — the `AppDatabase` class. Its `_openConnection()`
  function opens a `NativeDatabase.createInBackground` (SQLite runs on a background isolate so DB
  work never blocks the UI thread) pointed at a file named `app_template.sqlite` inside
  `path_provider`'s `getApplicationDocumentsDirectory()`. On iOS this is the app's `Documents/`
  sandbox; on Android it's the app's private `files/` directory — private storage that's wiped on
  uninstall.
- `AppDatabase.forTesting(NativeDatabase.memory())` is the in-memory variant used by tests (see
  `test/repository_test.dart`) — no file I/O, wiped automatically per test.
- `lib/core/di/database_providers.dart` — the single Riverpod provider (`appDatabaseProvider`,
  `keepAlive: true`) that hands out one shared `AppDatabase` instance app-wide and closes it via
  `ref.onDispose(db.close)`.

## Which files are responsible for what

| File | Responsibility |
|---|---|
| `lib/core/database/app_database.dart` | The `AppDatabase` class itself: table registration, schema version, connection opening. |
| `lib/core/database/app_database.g.dart` | Generated by `drift_dev`/`build_runner` — never hand-edit. |
| `lib/core/database/sync_queue_table.dart` | `SyncQueueEntries` table — the optional outbox queue (Strategy C, see `docs/architecture.md` §5). |
| `lib/features/<feature>/data/local/<name>_table.dart` | One Drift table definition per feature, e.g. `counter_table.dart`. |
| `lib/core/di/database_providers.dart` | The provider that hands out the shared `AppDatabase` instance. |
| `lib/features/<feature>/data/datasources/<name>_local_datasource.dart` | An abstract interface (e.g. `CounterLocalDatasource`) plus a concrete Drift implementation (e.g. `DriftCounterLocalDatasource`) — this is the layer repositories actually depend on, never `AppDatabase` directly. |

Repositories only ever call a feature's `*LocalDatasource` interface, not `AppDatabase` directly
(the outbox insert in `counter_repository_impl.dart`'s Strategy C block is the one exception, since
sync is cross-cutting rather than feature-owned). That indirection is what makes swapping the
underlying engine possible without touching `domain/` or `presentation/`.

## Swapping Drift for another local storage plugin

There are two different levels of "swap" here, because today the clean interface boundary only
exists at the per-feature layer — it doesn't (yet) extend to the core database/sync modules.

### A. Swap it for one feature (supported today, no core changes needed)

1. Add the new plugin's dependency (`hive`, `isar`, `sqflite`, `objectbox`, etc.) to `pubspec.yaml`
   — flag it to the user before adding it.
2. Implement that feature's existing local datasource interface with the new plugin instead of
   Drift, e.g. `HiveCounterLocalDatasource implements CounterLocalDatasource`.
3. Swap the single binding in that feature's Riverpod provider (e.g.
   `counterLocalDatasourceProvider` in `counter_controller.dart`) to return the new
   implementation.
4. Nothing in `domain/` or `presentation/` changes — this is the same one-line swap shape as the
   REST↔Firebase remote-backend swap (see the `api-data-sync` skill).

### B. Replace Drift as the app's core local engine entirely (a real migration, not a config flip)

This is a bigger job because these pieces are Drift-specific today:

- `lib/core/database/` (`AppDatabase`, `sync_queue_table.dart`, and every feature's
  `*_table.dart`) — schema definitions would need to be rewritten in the new engine's format.
- `lib/core/sync/sync_queue_processor.dart` — currently takes a Drift `AppDatabase` and queries
  `_db.select(_db.syncQueueEntries)` directly; it would need a storage-agnostic queue
  representation instead.
- Every feature's `Drift*LocalDatasource` implementation would need rewriting, one by one.

There's no shortcut for this path today — treat it as a genuine migration if a project ever needs
it app-wide, rather than assuming it's a single provider swap like option A.
